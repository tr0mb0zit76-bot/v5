# Архитектура ИИ-слоя CRM: целевая модель и фаза MVP

Документ задаёт направление развития и границы ответственности между CRM, локальным AI-контуром и внешними LLM. Реализация может опережать инфраструктуру: допускается **временное «эрзац»-решение**, пока не накоплены объём и зрелость процессов для полноценного второго уровня.

---

## 1. Три уровня (куда идём)

### Уровень 1 — CRM + MySQL

- Учёт заказов и связанная первичная бухгалтерия, контрагенты, простой BI.
- Системная «истина» по операционным данным; основной OLTP-контур.
- То, без чего бизнес не работает даже при отключении AI.

### Уровень 2 — собственный AI-контур (целевая платформа на отдельном сервере)

- Малые языковые модели, эмбеддинги, вектора (например Qdrant), сервисы индексирования оргзнаний.
- Обслуживание ИИ-ассистентов продукта: тренажёр, помощники по ролям, привязка к сценариям и объектам CRM.
- **Двустороннее обогащение знаний компании**: сотрудники → база знаний (уточнения, кейсы); система → лучшие подсказки и поиск для следующего шага.
- Здесь **допускается и ожидается привязка к собеседнику** (пользователь, роль, сессия тренировки, контекст узла скрипта и т.д.), чтобы точнее подбирать ответ и фиксировать обратную связь.

Запуск в проде предполагается через **Docker** (повторяемые окружения, проще воспроизведение перед выносом на выделенный хост).

### Уровень 3 — большие модели через API (внешние провайдеры)

- Подключение по API-ключам для задач, которые выходят за рамки «личной»/малой модели: глубокий метаанализ, редкий сложный синтез, черновики «сырого масштаба» при жёстких лимитах по локальной мощности.
- На этот контур данные должны попадать **уже обезличенными** (или минимально агрегированными); прямых ПИИ, идентификаторов сделок и сырых персональных имён из CRM — по политике ниже не передаём без отдельного решения по комплаенсу.

## 2. Политика данных между уровнями

| Область | Уровень 2 (свой AI) | Уровень 3 (большая модель) |
|--------|---------------------|----------------------------|
| Идентификация сотрудника/сессии | Допустимо для точности контекста и обучения в контуре | Не использовать; только обезличенные ярлыки при необходимости |
| Содержимое переписок, ФИО, телефоны, контрактные суммы как есть | По правилам продукта и доступа CRM | По умолчанию **нет** |
| Продукт и скрипт (обезличено) | Да | Да |
| Метки исхода, агрегаты качества диалогов | Да для анализа внутри L2 | Только если обезличено и утверждено |

**Обязательно заложить в код**:

- Одна точка принятия решения «уйти ли запрос во внешний API» (`gate` или сервис-обёртка).
- Слой **обезличивания/redaction** перед вызовом уровня 3 (whitelist полей или шаблонов).
- Логирование типа канала ответа: `local_small | external_large` без утечки чувствительного тела промпта в общие логи.

При расхождениях между удобством и безопасностью **предпочтение за меньшим объёмом данных на уровне 3**.

## 3. Фаза MVP: «эрзац» второго уровня

До запуска выделенного сервера уровень 2 **логически существует**, но **технически разнесён**:

- часть задач выполняется **в Laravel** на сервере CRM (правила, сессии тренажёра, сохранение реплик, выбор сценария);
- генерация текста и тяжёлые возможности временно делегируются **сразу на уровень 3** (как уже сделано для отдельных сценариев), возможно без локального embedding-поиска;
- когда появится наполненный корпус и стабильный ingestion — **эмбеддинги и малая модель переезжают** в явный второй контур без смены смысла продуктовых флоу.

Цель этой фазы — **не ждать идеальной инфраструктуры**, а отрабатывать продукт, объёмы данных и границы обезличивания.

Критерии, после которых имеет смысл закрепить **полноценный уровень 2 на своём железе** (ориентир, не закон):

- есть устойчивый пайплайн загрузки знаний и измеримая польза от семантического поиска;
- нагрузка или latency мешает держать всё только на узле CRM;
- появились регламенты на хранение вектора и версии моделей.

## 4. Инфраструктура Docker и переезд

- Контуры уровня 2 описываем как **композицию контейнеров** (малая модель, Qdrant, вспомогательные воркеры) — сначала **на том же хосте, что CRM**, затем образы и те же `docker-compose` профили можно перенести на отдельный сервер.

- После переезда для приложения в основном меняются **конфигурация и секреты** (URLs, ключи API внутреннего inference, таймауты, допуск по сети). Если **не менять** модель эмбеддингов и размерность, индекс в Qdrant можно перенести через snapshot или переиндексацию; смена модели эмбеддингов = **пересборка индекса**, не только `env`.

- В Laravel выгодно сразу вводить **абстракцию клиента**: «поиск по знаниям», «локальный inference» — один интерфейс, несколько backend-конфигов (локальный заглушка / удалённый URL).

## 6. План работ (бэклог, чеклист)

Используем как дорожную карту; порядок можно менять по приоритетам продукта.

### Контракты и код CRM (уровень 1 + «эрзац» L2)

- [x] **`ChatCompletionClient` + `DeepSeekChatCompletionClient` + `TrainerChatCompletionService`** — единая точка вызова чата (см. `app/Contracts/Inference`, `AppServiceProvider`). Заглушка без ключа: поведение как раньше (сообщение про `DEEPSEEK_API_KEY` до вызова API).
- [x] **`AiRequestGate`** — для command bar: `local_only` без ключа DeepSeek, иначе `external_large` (см. `App\Services\Agents\AiRequestGate`).
- [x] **`ExternalLlmPayloadSanitizer`** — redaction PII и чувствительных полей перед DeepSeek; профили `command_bar` / `trainer` (`config/ai.php`).
- [x] **Структурированный аудит (v1)** — таблица `ai_interaction_events`: `channel`, `feature`, `outcome`, обезличенные промпт/ответ, tools, `duration_ms`, `tokens_*`; MCP/command bar tool `get_ai_usage_insights`.
- [ ] **Структурированный аудит (v2)** — тренажёр, экспорт в data lake, партиционирование.
- [ ] **Расширить `config/ai.php`** — таймауты, URL будущего локального inference, feature-flags.

### Тренажёр и сценарии

- [ ] **Проброс контекста текущего узла скрипта** в промпт тренажёра (по желанию, особенно для режима «ИИ — продавец»).
- [ ] **Парсинг строки «Для менеджера: …»** из ответа модели → отдельное поле или таблица `trainer_coach_tips` для аналитики и будущего RAG.
- [ ] **Экспорт выборки диалогов** для разметки/ingestion (фильтр по `trainer_ai_role`, дате; обезличивание при выдаче).

### Знания и вектора (после старта наполнения)

- [ ] **Интерфейс `KnowledgeSearch` / `EmbeddingIndex`** — `upsertChunk`, `nearest`; реализации: `Null*`, `Qdrant*` за конфигом.
- [ ] **Команда/джоб индексации** источников (книга продаж, статические базы знаний) с метаданными `embedding_model`, `chunk_size`.
- [ ] **`docker-compose` профиль AI** на текущем сервере: Qdrant + inference; порты только internal / VPN.
- [ ] **Процедура snapshot Qdrant** и переноса коллекций на другой хост (тот же compose, другие `.env`).

### Уровень 3 и обезличивание

- [ ] **Явный список сценариев**, где разрешён вызов внешней большой модели (конфиг или enum feature-ключей).
- [ ] **Краткий регламент redaction** для команды (1 страница): что можно/нельзя передавать в API в MVP.

### Когда выносить полноценный L2 на отдельное железо

- [ ] Собрать метрики: p95 latency чата, таймауты, объём индекса, RPS embeddings.
- [ ] Перейти после стабильного ingestion **или** при превышении порога нагрузки на узел CRM (пороги зафиксировать заранее).

### STT / Whisper (пауза до GPU)

- **Сейчас:** браузерный Web Speech за фасадом `resources/js/support/speechToTextSession.js` (UI лида). Не плодить Web Speech по страницам.
- **Цель L2:** локальный Whisper на GPU-сервере → `SpeechTranscriptionService` + тот же фасад / command bar (mic, файлы звонков).
- **Статус:** ⏸ пауза до появления GPU-хоста; см. `docs/commercial-intelligence-roadmap.md` → «Голосовой ввод (STT)».
- Не закреплять внешний Whisper API как постоянный контур для записей звонков с ПДн.
