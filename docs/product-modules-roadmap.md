## 1. Претензии (Claims) — MVP для Юрика

**Цель:** спор/инцидент по рейсу перестаёт жить в заметках и мессенджере; появляется учёт, статусы и работа юриста/СБ.

### Сущности (черновик)

- `order_claims` (или `claims`): заказ, сторона (`customer` / `carrier` / `internal`), тип, сумма риска, валюта, статус, описание, ответственный, сроки.
- Связи: `order_id`, опц. `contractor_id`, вложения (через существующие order documents / отдельный disk path), ссылки на mail_thread / activity_events.
- Ledger: события `ClaimOpened` / `ClaimStatusChanged` / `ClaimClosed`.

### Статусы (v1)

`draft` → `open` → `in_review` → `negotiating` → `resolved` | `rejected` | `written_off`

### Типы (каталог)

Простой / порча / срыв срока / спор по ставке / документы / иное.

### UI

- Вкладка или блок в заказе «Претензии» + реестр `/claims` (грид).
- Карточка претензии: поля, лента, вложения, задача «Юрику».
- Меню: область видимости `claims` или reuse `orders` + роль юриста; feature `claims`.

### Ассистент Юрик

- Tools: `list_order_claims`, `get_claim`, `create_claim_draft`, `suggest_claim_next_step` (по базовым условиям / прецедентам из Книги — позже).
- Не заменяет юриста: формулировки с оговоркой «требует проверки».

### Критерий MVP

Менеджер заводит претензию с заказа за &lt;1 мин; руководитель видит открытые в гриде; в Ledger есть след; Юрик отвечает по tool, а не «из воздуха».

**Сделано в коде (2026-07-20):** таблица `order_claims`, feature `order_claims`, вкладка в заказе, реестр `/claims`, события Ledger `claim_*`. MCP tools для Юрика — следующий шаг.

### Вне MVP (сразу не делать)

Автоштрафы из графика, интеграция со страховой, полноценный документооборот претензии в ЭДО.

## 4. RFQ / котировки (после Claims MVP)

**Цель:** на лиде/закупке — несколько ставок перевозчиков, выбор победителя → предрасчёт/заказ.

- Сущность `lead_rate_quotes` / `procurement_quotes` (lead_id или load_board_post_id, contractor, rate, currency, valid_until, source, status).
- UI: таблица офферов + «выбрать» → `target_price` / performer.
- Стык с load-board офферами — не плодить второй мир без нужды.

## 7. Playbooks как продукт

**Цель:** один клик «включить пакет» на БП: этап → coaching_hint / статья / обязательные поля / auto_create_task.

- Каталог пакетов (seed) + UI в настройках БП «Применить playbook».
- Опора: уже есть `BusinessProcessPlaybook*`, `automated_actions` на этапах.

---

## 8. Портал заказчика (лёгкий)

**Цель:** симметрия portal перевозчика — клиент по токену видит статус рейса и скачивает согласованные доки.

- Публичный route без auth CRM (как verify PDF).
- Минимум полей: номер заказа, этапы маршрута (план/факт без лишнего), список файлов с `party=customer` / outgoing.
- Не строить полноценный B2B-кабинет в v1.
