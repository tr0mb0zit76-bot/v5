## Зачем отдельный roadmap

Текущая CRM — **vertical product** под логистику (заказы, документы, график оплат, учёт, Traklo, скрипты). Переход к SaaS — не «добавить регистрацию», а **multi-tenant продукт + биллинг + изоляция + упрощённый MVP для арендаторов**.

Оценка уже сделанного (ориентир): эквивалент **~4 000–6 000 ч** классической разработки, рыночная стоимость создания **~15–25 млн ₽**; календарь с Cursor — **~3 месяца**.

## Фаза 0 — продуктовая гипотеза (без кода)

**Цель:** понять, что именно сдаём в аренду и кому.

### Вопросы для проработки

| Тема | Варианты / заметки |
| --- | --- |
| **ICP** | экспедиторы 5–50 чел.; только РФ; нужен mobile/Traklo в day-1? |
| **MVP SaaS** | лиды + заказы + контрагенты + базовые документы? без управленки/биржи? |
| **Дифференциатор** | логистика + документы + график оплат + KPI — не «ещё одна CRM» |
| **Тарифы** | места, заказы/мес, объём файлов, модули (add-on) |

## Фаза 1 — tenancy и изоляция (технический фундамент)

**Рекомендуемый старт:** **single database + `tenant_id`** на бизнес-таблицах (до ~50–200 клиентов). Schema/DB per tenant — позже, под enterprise.

### Обязательный минимум

- [ ] модель `Tenant`, связь `users.tenant_id`
- [ ] `tenant_id` на: `orders`, `leads`, `contractors`, `tasks`, `documents`, …
- [ ] middleware **`IdentifyTenant`**: subdomain (`acme.crm.ru`) или custom domain
- [ ] global scopes / политики — **ни один query без tenant**
- [ ] файлы: `storage/tenants/{id}/…`
- [ ] jobs/queues с tenant context
- [ ] тесты: tenant A **никогда** не видит данные tenant B
- [ ] super-admin: список tenants, suspend, audit (impersonate — только с логом)

### Пакеты / паттерны

- рассмотреть `stancl/tenancy` как базу; домен настолько свой, что **большая часть — кастом**
- **tenant #1 = текущий prod «Автоальянс»** — миграция без «второго продукта с нуля»

### Оценка (грубо)

| Блок | Недели (1–2 senior) |
| --- | --- |
| схема + миграции tenant_id | 3–5 |
| middleware + scopes + тесты изоляции | 2–4 |
| storage, очереди, seed demo tenant | 1–2 |
| super-admin shell | 2–3 |

## Фаза 2 — онбординг и биллинг

- [ ] signup → создание tenant → wizard (название, часовой пояс, валюта)
- [ ] trial (14 дней) → оплата (**ЮKassa / CloudPayments / Stripe** — не свой биллинг)
- [ ] лимиты: пользователи, заказы/мес, storage
- [ ] блокировка tenant при неоплате (read-only / suspend)
- [ ] email: welcome, trial ending, invoice

## Фаза 3 — продуктовый MVP для арендаторов

**Принцип:** не 100% parity с внутренней CRM — **модульная упаковка**.

### Ядро (все тарифы)

- auth, роли, `visibility_areas` (уже есть — хорошая база)
- лиды, заказы, контрагенты, задачи
- базовый грид + saved views
- один subdomain

### Add-on / Pro

| Модуль | Заметка |
| --- | --- |
| документы + чек-лист | упрощённые правила vs полный регламент AA |
| график оплат | возможно упрощённый installment JSON |
| печать DOCX / verify | Gotenberg, шаблоны per tenant |
| скрипты + тренажёр + Книга | контент per tenant |
| управленческий учёт + бюджет | только Pro+ |
| биржа грузов / закупка | только Pro+ или отдельный SKU |
| Traklo / mobile / external | отдельный tier, много security |

## Фаза 4 — безопасность и операционка

До первого paying customer:

- [ ] audit log (заказы, деньги, роли)
- [ ] backup / restore (хотя бы daily + restore drill)
- [ ] staging + CI (pint, tests, build) — см. handoff «Окружение»
- [ ] миграции на N tenants (очередь, не ручной SSH)
- [ ] rate limits, 2FA для tenant-admin
- [ ] runbook: onboarding клиента ≤ 30 мин

---

## Что не делать в первые 6 месяцев SaaS

- white-label = отдельный fork кода на клиента
- полный feature parity с внутренней CRM
- кастом в коде под каждого (только settings + feature flags)
- custom domain для всех с day-1
- перенос всей управленки/биржи в base tier

## Риски

| Риск | Митигация |
| --- | --- |
| утечка данных между tenants | тесты + code review + pentest на изоляцию |
| «прод AA сломали tenancy-рефакторингом» | tenant #1 first, feature flags |

| домен слишком узкий для mass SaaS | vertical SaaS «для экспедиторов» — ок, не generic CRM |
