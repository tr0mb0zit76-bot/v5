# Регламент работы с документами в CRM «Автоальянс»

**Версия:** 1.0 (черновик для утверждения)  
**Дата:** 2026-06-07  
**Область:** документы по заказам в CRM (реестр, мастер заказа, портал перевозчика)

**Связанные материалы:** [Инструкция пользователя](documents-user-guide.md) · [Мастер заказов](order-wizard-user-guide.md)

---

## 1. Цель и область действия

1.1. Настоящий регламент устанавливает **единые правила** загрузки, проверки и актуализации документов в CRM.

1.2. Регламент обязателен для:

- менеджеров по перевозкам;
- делопроизводства и логистов;
- бухгалтерии (закрывающие документы);
- сотрудников, работающих с порталом перевозчика и реестром «Документы».

1.3. Документы контрагентов и автопарка (вне карточки заказа) готовятся **по тем же принципам** ориентации и качества файла; порядок загрузки — по инструкциям соответствующих разделов CRM.

---

## 2. Термины

| Термин | Значение |
| --- | --- |
| **Прикрепление** | Загрузка файла в CRM с указанием заказа, стороны, типа, номера и даты |
| **Метаданные** | Поля формы: заказ, сторона, тип, статус, номер документа, дата документа |
| **Печатная форма** | Заявка/договор, созданная из шаблона DOCX в workflow заказа |
| **Чек-лист документов** | Обязательные пункты на вкладке «Документы» для статусов «Оплата» / «Завершено»; при **наличных** у контрагента — только заявка, без УПД/СФ/акта |

---

## 3. Общие принципы

3.1. **Один заказ — один источник правды.** Актуальный скан или финальный PDF должен быть в CRM, а не только в почте или мессенджере.

3.2. **Ответственность за содержимое** несёт сотрудник, прикрепивший документ. CRM не проверяет автоматически соответствие даты в файле и даты в форме.

3.3. **Своевременность.** Документ вносится в систему **не позднее сроков** из раздела 6, даже если бумажный оригинал ещё в пути или лежит на столе.

3.4. **Качество файла.** Перед прикреплением документ приводится к стандарту (раздел 5). Загрузка «как есть» с телефона без проверки **не допускается**, если файл не читаем или не соответствует требованиям.

3.5. **Наличная оплата.** Если у контрагента в заказе указана форма оплаты **«Наличные»**, для закрытия сделки по нему **достаточно подписанной заявки**; УПД, счёт-фактура и акт **не являются обязательными** и не блокируют статус «Завершено». Комплект транспортных документов (ТН / ЭТрН / CMR / ТСД) остаётся обязательным по заказу в целом.

## 4. Проверка перед прикреплением (обязательно)

Перед нажатием «Добавить» / «Прикрепить» ответственный **лично** сверяет файл с карточкой заказа.

### 4.1. Чек-лист проверки

| № | Проверить | Действие при расхождении |
| --- | --- | --- |
| 1 | **Заказ** — документ относится к этому перевозочному заказу (номер, маршрут, контрагент) | Не прикреплять; уточнить у автора документа |
| 2 | **Сторона** — заказчик / перевозчик / подрядчик / внутренний | Исправить в форме |
| 3 | **Тип** — заявка, договор, ТТН, УПД, акт и т.д. | Выбрать верный тип (влияет на реестр и чек-лист) |
| 4 | **Номер документа** в CRM = номер в тексте документа | Ввести фактический номер с бланка |
| 5 | **Дата документа** в CRM = дата в документе (не дата скана и не дата отправки почтой) | Ввести дату с бланка |
| 6 | **Подписи и печати** — на скане видны все требуемые подписи на момент загрузки | Догрузить актуальную версию, не оставлять устаревший скан |
| 7 | **Статус** — черновик / ожидает / подписан / отправлен отражает реальность | Для закрывающих и ТТН после подписания — «Подписан» или «Отправлен» |
| 8 | **Плечо / перевозчик** — при нескольких плечах выбран правильный исполнитель | Указать плечо или перевозчика в форме прикрепления |

### 4.2. Типичные ошибки (запрещены)

- Дата в CRM — «сегодня», в документе — другая дата подписания.
- Прикреплён черновик без подписи при статусе «Подписан».
- В системе старая версия, а на руках уже документ с **двумя подписями** (см. раздел 6).
- Перепутаны заказчик и перевозчик (особенно зеркальные заявки).
- Тот же файл прикреплён к другому заказу «для скорости».

### 4.3. Фиксация ответственности

Сотрудник, прикрепивший документ, подтверждает, что выполнил чек-лист §4.1. При последующем аудите расхождения разбираются с **последним загрузившим**, если не доказано иное.

## 5. Подготовка файла к стандарту (до загрузки)

### 5.1. Формат

- Предпочтительно: **PDF** (один файл = один логический документ).
- Допустимо: JPG/PNG **только** если PDF получить невозможно; несколько фото — **собрать в один PDF** перед загрузкой.
- DOC/DOCX — для подписанных бумаг **после** сканирования; editable Word в реестр не загружать как «подписанный».

### 5.2. Ориентация и читаемость

| Требование | Пояснение |
| --- | --- |
| Книжная (A4 portrait) | Страница вертикально, текст не «лежит на боку» |
| Альбомная | Страница повёрнута **горизонтально**, содержимое читается без поворота головы в просмотрщике |
| Обрезка | Нет лишних полей с фоном стола; документ занимает кадр |
| Разрешение | Достаточно для чтения реквизитов и подписей; **избыточные** 600+ DPI не использовать |
| Цвет | Достаточно оттенков серого для текстовых документов; цвет — если важны печати/штампы |

Перед загрузкой откройте PDF в просмотрщике **постранично** и убедитесь, что все страницы ориентированы правильно.

### 5.3. Размер файла

Ориентиры (не жёсткий лимит CRM, а **норма подготовки**):

| Тип | Целевой размер |
| --- | --- |
| Текстовая страница A4 (скан) | **200–800 КБ** на страницу |
| Страница с цветной печатью | до **1,5 МБ** на страницу |
| Многостраничный договор | суммарно разумно для передачи по почте (< 15–20 МБ) |

**Недопустимо** без предварительной оптимизации:

- одна страница PDF **несколько мегабайт** из-за необрезанного фото с телефона;
- «сырой» экспорт со сканера без сжатия;
- дубликаты одной страницы в файле.

CRM ограничивает загрузку по **бюджету страниц** (~600 КиБ × число страниц, см. подсказку в форме). Слишком тяжёлый файл может быть **отклонён** — это не повод обходить правило, файл нужно **сжать до загрузки**.

### 5.4. Рекомендуемые инструменты (на рабочем ПК)

- Поворот / объединение страниц: Adobe Acrobat, PDF24, «Печать в PDF» после исправления ориентации.
- Сжатие сканов: встроенное «Reduce file size» / «Optimize» в PDF-редакторе, PDF24 Compress.
- Сканеры: профиль «Документ / PDF», не «Фото максимального качества».

*Список может дополняться IT; использование облачных сервисов с передачей данных **контрагентов** — только если это согласовано с политикой безопасности компании.*

### 5.5. Автоматическая оптимизация в CRM

При превышении лимита размера **PDF** CRM предлагает оптимизацию на сервере, предпросмотр и подтверждение (использовать файл / отмена и ручная подготовка).

Требует OCR_SERVICE_URL и DOCUMENT_OPTIMIZE_ENABLED=true. Sidecar: POST /optimize, CRM: POST /documents/optimize-pdf.

Для DOCX/JPG и при отключённом sidecar — только ручная подготовка по §5.2–5.4.

## 6. Своевременность и актуальность

### 6.1. Сроки внесения в CRM

| Событие | Срок прикрепления / обновления |
| --- | --- |
| Подписанная **заявка** / **договор-заявка** (наша или контрагента) | **В тот же рабочий день** получения подписанного экземпляра, не позднее **следующего рабочего дня** |
| **ТТН / CMR / ЭТрН** после выгрузки | **Не позднее 1 рабочего дня** после получения от перевозчика |
| **Закрывающие** (УПД, акт, счёт-фактура) | **В день получения**, не позднее **1 рабочего дня** (не требуются при оплате **наличными** — см. §3.5) |
| **Доработанный** документ (вторая подпись, исправленный бланк) | **В день** появления новой версии; старую версию **заменить** или явно довести статус (см. §6.3) |
| Документ от перевозчика через **портал** | Менеджер проверяет и принимает в CRM **в тот же день** поступления уведомления |

Сроки исчисляются по календарю **Europe/Samara**. «Получение» = фактическая доступность скана/оригинала сотруднику компании (курьер, почта, ЭДО, мессенджер).

### 6.2. Запрет «бумага есть — скана нет»

Запрещается ситуация, когда:

- оригинал с **двумя подписями** уже в офисе или у контрагента,
- а в CRM **нет** актуального скана или финального PDF,

**и** при этом заказ переведён в стадии, предполагающие наличие документа (чек-лист, оплата, завершение).

Ответственный менеджер обязан **до** запроса оплаты / закрытия заказа убедиться, что чек-лист на вкладке «Документы» **закрыт актуальными** файлами.

### 6.3. Обновление версии

Если документ переподписан или заменён:

1. Загрузить **новый файл** с корректными метаданными (дата/номер по новой версии), **или**
2. Заменить файл в карточке (если доступна операция замены), **или**
3. Для печатной формы — довести workflow до нового финального PDF.

Устаревший скан **не оставлять** как единственный при наличии более новой версии на бумаге.

### 6.4. Контроль

- Руководитель направления / старший менеджер — **еженедельная** выборочная проверка 5–10 заказов в статусах «Документы» / «Оплата» / «Завершено».
- Делопроизводство — сверка реестра «Документы» с фактическими папками/ЭДО **не реже 1 раза в месяц**.
- Нарушения сроков §6.1 фиксируются на планёрке; систематические — на рассмотрение руководства.

## 7. Порядок работы в CRM (кратко)

| Действие | Где в CRM |
| --- | --- |
| Заявка из шаблона | Заказ → «Документы» → печатная форма → workflow → финальный PDF |
| Скан подписанного | «Прикрепить файл» на вкладке «Документы» **или** реестр «Документы» → «Добавить документ» |
| Массовый обзор | Меню «Документы» → реестр; двойной клик — все файлы заказа |
| Заполнение заказа из PDF клиента | «Новый заказ» → «Заполнить из заявки» (это **не** заменяет прикрепление подписанной заявки) |

Подробно: [documents-user-guide.md](documents-user-guide.md).

## 8. Портал перевозчика

8.1. Документы, загруженные перевозчиком, **не считаются** проверенными автоматически.

8.2. Менеджер обязан в срок §6.1 выполнить чек-лист §4.1 и при необходимости **перезагрузить** исправленный файл от имени компании.

```
[ ] Заказ и контрагент совпадают

[ ] Подписи на скане соответствуют статусу

```

## Приложение B. Технические лимиты CRM (справка)

- Оценка лимита загрузки: ~**600 КиБ × число страниц** (макс. ~200 стр.) — см. подсказку в форме.
- Хранение файлов: Nextcloud (WebDAV) или локальный диск — см. `config/document_storage.php`.
- OCR sidecar: POST /optimize — сжатие PDF при загрузке (с подтверждением). POST /extract — распознавание заявки.
