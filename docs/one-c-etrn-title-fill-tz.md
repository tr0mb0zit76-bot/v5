# ТЗ для подрядчиков 1С: заполнение титула исходящей ЭТрН из CRM

**Дата:** 2026-08-27  
**Заказчик:** CRM «Автоальянс» (v5)  
**ИБ (тест):** `Avtoalyans_test_VR9WFLDPD4` на `https://avtoalyns-crm.case-it.ru/...`  
**ИБ (прод):** `Avtoalians_4nYnMmRSab`  
**OData:** Basic Auth (`odata` / учётные данные публикации), путь `/odata/standard.odata/`

Документ можно переслать как есть команде, которая обслуживает сервер 1С и публикацию OData.

---

## 1. Цель

CRM умеет создать **каркас** документа `Электронная транспортная накладная` и проставить стороны.  
Нужно, чтобы после вызова с вашей стороны (или через ваш API) в форме ЭТрН на этапе **«Оформление»** были заполнены те же поля, которые менеджер сейчас вводит кнопками **«Заполнить»**:

- грузоотправитель / грузополучатель / перевозчик (с телефонами);
- номер и дата заказа (заявки);
- адрес погрузки и адрес доставки;
- сведения о грузе;
- водитель;
- транспортное средство;
- указания ГО (если есть в CRM — опционально).

Без отправки оператору ЭДО (Астрал) на этом этапе. Достаточно **сохранённого черновика**, который человек открывает в 1С и видит заполненные поля (не только комментарий).

---

## 2. Что CRM уже делает сама (через OData)

Проверено на тестовой ИБ, документ № `00000000005` (заказ CRM `АС-СН-949`, id 189).

| Действие | Статус |
| --- | --- |
| `POST Document_ЭлектроннаяТранспортнаяНакладная` | ✅ создаётся черновик (`Posted=false`) |
| `Организация_Key`, `Date`, `Комментарий` | ✅ |
| `ТитулГрузоотправителяТранспортнаяНакладнаяНомер/Дата` | ✅ |
| `СсылкаТитулГрузоотправителя{Заказчик,Грузоотправитель,Грузополучатель,Перевозчик}` + `_Type=Catalog_Контрагенты` | ✅ |
| Создание/поиск контрагента по ИНН/КПП, запись телефона в `КонтактнаяИнформация` (`ТелефонКонтрагента`) | ✅ |
| Сводка маршрут/груз/водитель/ТС в `Комментарий` (лимит ~250 символов) | ✅ обходной путь |

**Проблема:** в UI поля формы (адрес, груз, водитель, ТС, «номер заказа») остаются пустыми / с «Заполнить», хотя ссылки на контрагентов и телефоны в карточках уже есть.  
Причина: эти данные живут в **титульных структурах** конфигурации ЭПД, а не в реквизитах шапки документа, доступных в стандартном OData (у EntityType ~80 свойств, из них нет адреса/груза/водителя/ТС).

`Catalog_ХранимыеДанныеЭПД` в публикации есть, но запись туда **не подставляет** значения в открытую форму документа (это справочник шаблонов, не привязка к полям титула формы).

FunctionImport / Action для заполнения титула в `$metadata` **нет**.

### Вариант B: расширить OData-публикацию

Если титул хранится в сущностях, которые можно писать через OData:

1. Перечислить EntitySet / ТЧ / регистры, куда форма пишет данные титула ГО.
2. Включить их в публикацию `standard.odata` (чтение + запись).
3. Дать нам **пример успешного POST/PATCH** (Postman/лог), после которого форма ЭТрН показывает адрес/груз/водителя/ТС.

Мы сами реализуем вызовы из CRM.

### Вариант C: экспорт/импорт XML титула

Если штатный путь — сформировать файл титула ГО и привязать к документу (`ТитулГрузоотправителяИдентификаторФайла` и связанное хранилище):

1. Описать формат / XSD или дать образец XML исходящего титула ГО для черновика.
2. Описать, как привязать файл к документу через OData или HTTP-сервис, **без** отправки оператору.
3. Подтвердить, что после привязки форма «Оформление» показывает данные из файла.

## 4. Критерии приёмки (тест на `Avtoalyans_test`)

Исходный документ: ЭТрН № `00000000005` (или новый, созданный CRM тем же способом).

После вашего метода:

| Проверка в UI 1С | Ожидание |
| --- | --- |
| Дата | заполнена |
| Номер заказа (заявки) | `АС-СН-949` (или согласованный маппинг) |
| Грузоотправитель / Грузополучатель / Перевозчик | наименования видны, без ошибки «Не заполнен номер телефона контрагента» |
| Адрес места доставки / погрузки | адреса из CRM |
| Сведения о грузе | наименование + масса |
| Водители | ФИО из CRM |
| Сведения о ТС | госномера тягач/прицеп |
| Проведение / отправка ЭДО | **не** выполнены автоматически |

Демо: один вызов на тестовой ИБ + скрин формы «Оформление» до/после.

## 5. Ограничения и договорённости

- CRM **не** подписывает титулы и **не** шлёт их оператору ЭДО в этой задаче.
- ГО и ГП для части заказов могут совпадать с заказчиком (как в примере 189) — это нормально; позже появятся отдельные стороны.
- Часть полей водителя (серия/номер ВУ) в CRM может быть пустой — тогда оставляете пустым или warning, не падаете целиком.
- Логин OData на тестовой ИБ: `odata` (lowercase); на прод-публикации часто `Odata` — если делаете отдельный HTTP-сервис, лучше единый сервисный пользователь.
