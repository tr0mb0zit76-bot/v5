# Commercial Intelligence — дорожная карта

Живой план модуля **Activity Ledger + почта + коммерция + (далее) аналитика и AI**.  
Фазы **0–1 реализованы** в коде; ниже — черновики следующих фаз для корректировки перед стартом.

**Связанные документы:**

- [commercial-intelligence-phase-0-1.md](./commercial-intelligence-phase-0-1.md) — что уже в проде по фазам 0–1 (краткая выжимка).
- [ai-platform-architecture.md](./ai-platform-architecture.md) — целевой ИИ-контур (фаза 6+ опирается на него).
- [nextcloud-install.md](./nextcloud-install.md) — NC только как WebDAV/хранилище.

**Легенда статусов:** ✅ сделано · 🚧 в работе · 📋 черновик (scope не зафиксирован)

---

## Принципы (не менять без явного решения)

| Решение | Статус |
|--------|--------|
| Nextcloud — **хранилище** файлов; встраивание CRM в NC не делаем | ✅ |
| Почта — **модуль CRM** (SMTP/IMAP), не NC Mail | ✅ |
| «Крутой комбайн» в одном продукте не цель; допустим набор приложений | ✅ |
| Персональные данные в письмах: раз в ~6 мес. для **не «важно»** — краткий контекст, тело удалить | ✅ (фаза 1) |
| Извлечение фактов в контрагента — только **HITL** (человек подтверждает) | 📋 |

## Фаза 2 — Входящая почта (IMAP) 📋

**Цель:** двусторонняя переписка в CRM, привязка к лиду/заказу/контрагенту, события `email_inbound` в Ledger.

| # | Задача | Готово, когда |
|---|--------|----------------|
| 2.1 | Настройки ящика: IMAP host, папки, OAuth/пароль (per company или per user) | Админка или `.env` + UI статуса |
| 2.2 | Job `mail:sync-inbound` (идемпотентность по `Message-ID`) | Новые письма в `mail_messages` |
| 2.3 | Обновление `last_inbound_at`, привязка к существующему `mail_thread` | Цепочка не дублируется |
| 2.4 | Автолинк: email отправителя → контрагент → открытый лид | Правила + ручное «привязать к лиду» |
| 2.5 | UI: просмотр цепочки, ответ из CRM (reply), флаг «важно» | Полноценная карточка переписки |
| 2.6 | Ledger + уведомление ответственному | Событие в таймлайне лида |

**Открытые вопросы:**

- Один общий ящик `sales@` vs личные ящики менеджеров?
- Свой почтовый сервер на VDS vs внешний relay (см. инфраструктуру)?
- Нужен ли парсинг вложений в NC автоматически?

**Критерий фазы:** входящее на общий ящик появляется в CRM и в ленте лида без ручного копипаста.

## Фаза 3 — Движок напоминаний (nudges) 📋

**Цель:** обобщить логику «нет ответа на КП» до правил воронки и SLA коммуникаций.

| # | Задача | Готово, когда |
|---|--------|----------------|
| 3.1 | Справочник типов nudge (`no_reply`, `stage_overdue`, `next_contact_missed`, …) | Config или таблица |
| 3.2 | Поля этапа БП: не только `no_reply_nudge_days`, но триггеры по событию Ledger | Настройка в «Бизнес-процессы» |
| 3.3 | `commercial:process-nudges` вместо узкой команды только для КП | Один планировщик |
| 3.4 | Дедупликация задач (как сейчас `meta->commercial_offer_no_reply_nudge`) | Нет дублей при повторном cron |
| 3.5 | UI: список «требует внимания» на дашборде / в лидах | Менеджер видит очередь |

**Критерий фазы:** правила на этапе БП создают задачи без правки PHP.

## Фаза 3.5 — Outcome Intelligence (коучинг по воронке) 🚧

**Цель:** ответы на «почему не закрываю сделки» на основе структурированных флагов закрытия и **пассивных сигналов** из CRM (этапы, квалификация, ledger, задачи) — без телефонии и синхронизации входящей почты.

| # | Задача | Готово, когда |
|---|--------|----------------|
| 3.5.1 | Флаги `close_outcome_primary_flag` на лидах + UI-чипы при `lost` / терминальном этапе | Менеджер закрывает проигрыш в 2 клика |
| 3.5.2 | `ManagerDealSignalExtractor` — hygiene score, **idle_dwell** vs **active_work** по activity_events | Долгое молчание не считается «подготовкой» |
| 3.5.3 | `ManagerSalesCoachingInsightsService` + MCP `get_manager_sales_coaching_insights` | Command bar отвечает с паттернами и примерами |
| 3.5.4 | Блок Outcome Intelligence на странице «Лиды» | Менеджер видит win rate и рекомендации |
| 3.5.5 | (Позже) обогащение после фазы 2 почты — «ответил / не ответил» | Не блокирует v1 |

**Не входит в v1:** телефония, IMAP, ML-прогноз риска на открытых лидах.

**Критерий фазы:** на закрытых лидах видны паттерны (нет ЛПР, idle на квалификации, частые флаги отказа); ассистент вызывает tool и цитирует факты.

## Сквозные требования (все фазы) 🚧

| # | Требование | Готово, когда |
|---|------------|----------------|
| X.1 | **Русские сообщения для пользователя** — сырые SQL/англ. тексты не показывать в UI (Inertia flash / JSON) | `UserFacingDatabaseMessageResolver` + баннер в `CrmLayout` |
| X.2 | **AI «знает всё» через tools** — один gate и стиль ответа, много доменных MCP (заказы, лиды, книга, coaching), не один монолитный агент | Расширение `AgentToolRegistry` + общий event log |
| X.3 | Удаление заказов и др. каскады — явный порядок FK / понятная ошибка «есть связанные данные» | Исправление `destroy` заказа + X.1 |

**Не делаем:** хранение «кто правил» статью/запись; полный audit revision log.

## Фаза 3.6 — Качество Книги продаж (Outcome Intelligence для базы знаний) 🚧

**Цель:** ориентировать правки статей на **оценки полезности**, а не на историю авторов. Связка с gap-аналитикой command bar.

| # | Задача | Готово, когда |
|---|--------|----------------|
| 3.6.1 | `sales_book_article_feedback` — оценки: полезно / непонятно / устарело (+ опц. комментарий) | UI на странице статьи |
| 3.6.2 | Агрегаты по статье + блок «требует правки» в Книге / AI-аналитике | Редактор видит топ проблемных |
| 3.6.3 | Связь thumbs command bar → `article_id` в metadata feedback | Gap по статье учитывается в агрегате |
| 3.6.4 | (Позже) `status` draft/published, теги, привязка статьи к этапу БП/узлу скрипта | Не блокирует 3.6.1 |

**Критерий фазы:** по статьям с накопленными «непонятно» видно, что переписать в первую очередь; ассистент цитирует только published (когда появится статус).

## Фаза 4 — Инсайты в карточку контрагента (HITL) 📋

**Цель:** из переписки и заметок предлагать факты; в CRM попадает только после подтверждения.

| # | Задача | Готово, когда |
|---|--------|----------------|
| 4.1 | Таблица `contractor_insight_drafts` (поле, значение, источник, confidence) | Черновики хранятся |
| 4.2 | Извлечение: эвристики / LLM по телу письма (только «важные» и не очищенные) | Job или по кнопке |
| 4.3 | UI: «Предложения по контрагенту» — принять / отклонить / править | HITL обязателен |
| 4.4 | Запись в поля контрагента + событие Ledger | Аудит откуда взялось |
| 4.5 | Связь с Activity Ledger (`source` = message / activity) | Клик → источник |

**Открытые вопросы:**

- Какие поля разрешено автозаполнять (телефон, должность, предпочтения по оплате)?
- Нужен ли запрет на LLM для сырых ПД (см. ai-platform-architecture)?

**Критерий фазы:** менеджер подтверждает черновик — поле контрагента обновляется, источник виден.

## Фаза 5 — Ценовая аналитика (маршруты, маржа) 📋

**Цель:** подсказки при просчёте лида/заказа на основе истории, без тяжёлого ML на старте.

| # | Задача | Готово, когда |
|---|--------|----------------|
| 5.1 | Витрина/запрос: маршрут (откуда–куда), тип ТС, сезон → min/avg/max ставки | SQL или materialized view |
| 5.2 | UI в лиде: «похожие перевозки» и диапазон | Рядом с `target_price` |
| 5.3 | Учёт валюты, НДС, типа контрагента (заказчик/перевозчик) | Не смешивать несопоставимое |
| 5.4 | (Опционально) экспорт в отчёты | Связь с модулем `reports` |

**Критерий фазы:** при вводе маршрута менеджер видит ориентир из своих же сделок.

## Фаза 6 — AI-ассистент в контуре коммерции 📋

**Цель:** черновики ответов, резюме переписки, следующий шаг — с опорой на Ledger и почту.

| # | Задача | Готово, когда |
|---|--------|----------------|
| 6.1 | Tooling: «резюме цепочки», «черновик ответа», «что сделать дальше по лиду» | API + UI в лиде/почте |
| 6.2 | Контекст: `activity_events` + важные `mail_messages` + книга продаж / скрипты | Лимит токенов, цитаты источников |
| 6.3 | Политика данных: L2 vs L3 по [ai-platform-architecture.md](./ai-platform-architecture.md) | Нет утечки ПД во внешний API без решения |
| 6.4 | Обратная связь (полезно/нет) для улучшения подсказок | Логи в CRM |

**Не смешивать с:** тренажёром продавца (отдельный модуль `sales_assistant_*`).

**Критерий фазы:** менеджер получает черновик ответа из контекста лида в 1–2 клика.

## Фаза 8 — Платформа CRM (идеи Odoo без монолита) 📋

**Цель:** декларативность, события, связи записей — по всей CRM, не только коммерция.

| # | Задача | Готово, когда |
|---|--------|----------------|
| 8.1 | Каталог **features** (вкл/выкл, `depends`) — routes, MCP, menu | Включение модуля без правки PHP |
| 8.2 | **Smart links** на карточках (статьи, coaching, gaps, задачи по лиду) | Счётчики на лиде/заказе |
| 8.3 | Правила на этапе БП: поле + статья + задача (automated actions) | Данные в `business_process_stages` |
| 8.4 | Наборы permissions в роли (implied groups) | Меньше ручной настройки |
| 8.5 | Тяжёлые job: reindex книги, отчёты | Очередь Laravel |

**Критерий фазы:** новый модуль включается флагом; менеджер видит связанные подсказки с карточки лида/заказа.
