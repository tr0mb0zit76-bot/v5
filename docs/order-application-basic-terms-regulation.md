# Регламент оформления заявки и изменения базовых условий

**Версия:** 1.0 (черновик для утверждения)  
**Дата:** 2026-06-07  
**Область:** заявки на перевозку (intake, мастер заказа), базовые условия cp/dp, печатные формы

**Связанные материалы:** [Ассистенты CRM](ai-assistants-user-guide.md) · [Мастер заказов](order-wizard-user-guide.md) · [Документы — инструкция](documents-user-guide.md)

---

## 1. Цель и область действия

1.1. Регламент устанавливает **единые правила** оформления заявки на перевозку в CRM и **изменения текстов базовых условий** в договорах-заявках (заказчик / перевозчик).

1.2. Обязателен для:

- менеджеров по перевозкам и продажам;
- делопроизводства;
- сотрудников, согласующих индивидуальные условия контрагентов;
- администраторов CRM (глобальные шаблоны и базовые условия).

1.3. Не заменяет **корпоративные договорённости с контрагентом** и **решение юриста** по спорным формулировкам.

---

## 2. Термины

| Термин | Значение |
| --- | --- |
| **Заявка (intake)** | Исходный текст или файл клиента до сохранения заказа в CRM |
| **Черновик intake** | Результат распознавания / разбора заявки; предзаполнение мастера заказа |
| **Мастер заказа** | Карточка заказа с вкладками (Основное, Маршрут, Груз, Финансы, Нормативы, Документы) |
| **Базовые условия** | Нумерованный список пунктов cp (заказчик) или dp (перевозчик), подставляемых в DOCX |
| **Печатная форма** | Заявка/договор, сгенерированная из шаблона по данным заказа |
| **Переопределение** | Индивидуальный набор условий на контрагенте или в конкретном заказе |

## 3. Оформление заявки на перевозку

### 3.1. Общий принцип

**CRM — единый источник правды.** Заказ создаётся и хранится в мастере; заявка клиента (PDF, DOCX, текст из почты) — **основа для ввода**, но не заменяет проверку менеджером.

### 3.2. Способы внесения заявки

| Способ | Когда использовать | Ответственный шаг после автоматизации |
| --- | --- | --- |
| **Новый заказ → «Заполнить из заявки»** | Есть файл PDF/DOCX заказчика | Проверить все вкладки → Сохранить |
| **Ассистент (Галя / Джарвис) + вложение или текст** | Удобно из command bar, заявка в переписке | Открыть предложенный мастер → проверить → Сохранить |
| **Ручной ввод в мастере** | Короткая заявка, нет файла | Заполнить обязательные поля → Сохранить |

Автоматическое распознавание **не прикрепляет** файл в «Документы заказа». После сохранения заказа подписанную заявку прикрепляют отдельно — см. [инструкцию по документам](documents-user-guide.md).

### 3.3. Обязательный минимум перед сохранением заказа

Перед первым **Сохранить** в мастере должны быть заполнены (система подсветит при отсутствии):

1. **Заказчик** (контрагент).
2. **Дата** заказа.
3. **Перевозчик** (или исполнитель на маршруте).
4. **Цена для клиента** (ставка заказчика).

Остальное (маршрут, груз, нормативы, документы) можно дозаполнить после сохранения, но **до отправки заявки контрагенту** данные должны соответствовать согласованной перевозке.

### 3.4. Чек-лист проверки после intake

| № | Проверить | При расхождении |
| --- | --- | --- |
| 1 | Заказчик, ИНН/название = заявке клиента | Исправить в «Основное» |
| 2 | Маршрут: адреса, города, плановые даты | Вкладка «Маршрут» |
| 3 | Груз: наименование, вес/объём, места | Вкладка «Груз» |
| 4 | Ставки заказчика и перевозчиков | «Финансы» |
| 5 | Тип перевозки (внутренняя / международная), своя компания | «Основное» (влияет на шаблоны) |
| 6 | Режим заявки: одна на все плечи или «разбить по плечам» | «Основное» |
| 7 | Нормативы и штрафы, если они в договоре | «Нормативы / штрафы» |

Менеджер **лично** отвечает за соответствие сохранённого заказа согласованию с клиентом.

### 3.5. Сроки

- Черновик intake обрабатывается **в день поступления** заявки (или в срок, установленный внутренним SLA подразделения).
- Заказ в CRM создаётся **до** выпуска заявки/договора из шаблона (печатная форма требует сохранённого заказа).

## 4. Базовые условия cp / dp

### 4.1. Назначение

**Базовые условия** — стандартный нумерованный блок текста в договоре-заявке:

- **cp (customer)** — для документов **с заказчиком**;
- **dp (carrier)** — для документов **с перевозчиком**.

Подставляются в DOCX через якорь шаблона (макрос списка условий). Переменные заказа (маршрут, ставка, даты) — **в шаблоне DOCX**, не внутри текста каждого пункта базовых условий.

### 4.2. Уровни применения (приоритет)

При печати действует **наиболее конкретный** уровень:

1. **Условия в заказе** (вкладка «Нормативы / штрафы») — для разовых отклонений по сделке.
2. **Условия контрагента** (Настройки → Базовые условия → выбранный контрагент).
3. **Общие условия** (по умолчанию для всех cp или dp).

Пустой список на контрагенте означает: **использовать общие** условия.

### 4.3. Формат пункта

1. **Один пункт = один элемент списка** в редакторе (отдельная строка/поле).
2. Нумерация в DOCX формируется **шаблоном**; в CRM хранится только текст пункта.
3. Если по договорённости пункт начинается с **«. »** (точка и пробел) — это **часть текста**, сохраняется как есть (типично для стиля нумерованных списков в Word).
4. Не дублировать в пунктах плейсхолдеры, которые уже есть в шаблоне (`${…}` / `{{…}}` для маршрута, сумм и т.д.), если они подставляются отдельными полями заказа.
5. Язык — **деловой русский**, без разговорных формулировок; аббревиатуры — общепринятые (ТС, ТТН, ЭТрН).

### 4.4. Кто и как меняет условия

| Изменение | Кто вносит | Как |
| --- | --- | --- |
| **Общие** cp/dp для всех | Администратор / settings_system | Настройки → Базовые условия → «Общие» → Сохранить **или** ассистент Юрик (при правах) |
| **Для одного контрагента** (менеджер) | Менеджер | Заявка на согласование (`submit_contractor_print_form_change`) или UI согласования; **не** прямое сохранение глобальных |
| **Утверждение / отклонение** | Руководитель | Решение по заявке в CRM (`approve` / `reject` / возврат на согласование с контрагентом) |
| **Разово по заказу** | Менеджер с правом редактирования заказа | Вкладка «Нормативы / штрафы» |

Прямое сохранение через `upsert_print_form_basic_terms` без согласования — **только** у ролей с правом управления настройками печати.

### 4.5. Процесс изменения общих условий

1. **Инициатор** (юрист, руководитель направления, администратор) формулирует изменения и обоснование.
2. **Черновик** правок вносится в «Общие» cp или dp (UI или Юрик с фиксацией версии в переписке/задаче).
3. **Проверка:** тестовая печать на типовом заказе — все пункты попали в DOCX (`get_print_form_templates_insights` при расхождениях).
4. **Уведомление** заинтересованных (менеджеры, делопроизводство) — по внутреннему каналу подразделения.
5. **Вступление в силу:** с момента сохранения; ранее созданные черновики DOCX **не пересобираются** автоматически — при необходимости пересоздать форму в заказе.

### 4.6. Процесс изменения условий контрагента

1. Менеджер фиксирует **отличия** от стандартных (письмо клиента, протокол, правки в договоре).
2. Подготавливает список пунктов cp или dp для этого контрагента.
3. Отправляет **заявку на согласование** (UI или Юрик) с кратким комментарием.
4. Руководитель **утверждает**, **отклоняет** или возвращает на согласование с контрагентом.
5. После утверждения условия применяются при следующей печати с участием этого контрагента.

## 5. Связь заявки, условий и печатной формы

```
Заявка клиента (файл/текст)
        ↓
Черновик intake → Мастер заказа (проверка менеджером)
        ↓
Сохранённый заказ
        ↓
Документы → Шаблон → Черновик DOCX
        ↑
Базовые условия (общие / контрагент) + поля заказа + нормативы
        ↓
Согласование → Финальный PDF → Прикрепление / отправка
```

**Запрещено:** менять базовые условия «задним числом» только в Word в обход CRM, если по этому контрагенту уже утверждён набор в системе — правки вносятся в CRM и повторно согласуются при необходимости.

---

## 6. Использование ассистента (Юрик / Галя)

6.1. Ассистент может **прочитать** текущие пункты, **предложить** черновик на основе carrier → customer, **отправить заявку** на согласование — в рамках прав пользователя.

6.2. Ответ ассистента по юридическим формулировкам **не является** юридическим заключением; финальную версию утверждает ответственный сотрудник.

6.3. Заявку на перевозку из файла через ассистента менеджер **всегда** верифицирует в мастере (раздел 3.4).

## 7. Ответственность

| Роль | Ответственность |
| --- | --- |
| **Менеджер** | Корректность данных заказа после intake; инициирование согласования индивидуальных условий |
| **Руководитель** | Утверждение / отклонение условий контрагента |
| **Администратор / settings_system** | Актуальность общих базовых условий и шаблонов DOCX |
| **Делопроизводство** | Соответствие выпущенного PDF данным заказа и утверждённым условиям |

## 8. Нарушения и типовые ошибки

| Ошибка | Риск | Действие |
| --- | --- | --- |
| Сохранён заказ без проверки intake | Неверный маршрут, ставка, контрагент | Исправить до выпуска документов; при отправке клиенту — эскалация руководителю |
| Пункты cp/dp в одной «простыне» вместо списка | Сбой нумерации в DOCX | Разбить на отдельные пункты в редакторе |
| Плейсholdеры в тексте пункта | Дубли или пустые места в договоре | Вынести в переменные шаблона |
| Правка общих условий без тестовой печати | Массовый брак в заявках | Откат версии, тест на эталонном заказе |
| Индивидуальные условия без согласования | Разночтения с регламентом компании | Оформить заявку на согласование задним числом или откатить |

---

## 9. Контроль и пересмотр

9.1. Администратор CRM **не реже 1 раза в квартал** проверяет актуальность общих cp/dp и соответствие шаблонам.

9.2. Регламент пересматривается при изменении процесса intake, структуры мастера заказа или модели согласования печатных форм.
